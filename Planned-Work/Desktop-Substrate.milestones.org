* Introduction
  :PROPERTIES:
  :initiative_goals: A dependency-free GuiAssert core (image maths, SSIM, video segmentation, pixel window detection, the OCR interface) plus opt-in capture, OCR, accessibility-tree, input and off-screen-session backends for macOS, Linux and Windows; a `guiassert` CLI and `guiassert serve` daemon with a frozen JSON contract and a deterministic fixture backend; Agent Harbor switched onto it platform by platform once parity is measured, and its duplicated native code removed only after parity holds everywhere.

  :END:

  Design, contract and rationale live in [[file:Desktop-Substrate.md]]. This
  file tracks execution, and it is the coordination point between two
  campaigns: this one (GuiAssert itself, macOS backends) and the companion
  campaign that owns every Agent Harbor change and the Linux backends. Both
  campaigns pull this file from =origin/agents= before starting a milestone and
  push their status updates to it.

  Milestones are implemented one at a time: an implementation agent (no
  commits) followed by an independent verification agent that runs the tests,
  rejects weak or skipped tests, and commits only on green.

  *Owner tags* (the =:owner:= property):
  - =substrate/macos= — this campaign, on its macOS development host (holds the
    TCC grants for live macOS evidence).
  - =companion/linux= — the companion campaign, on the organization's
    bare-metal Linux CI host; owns Agent Harbor's spec, backend crate,
    switch-over and removal, and may claim any Linux deliverable here.
  - =later/windows= — unowned until a Windows host is available; Windows
    deliverables run on the CI Windows class or that host.

  *Per-platform milestones.* GS5–GS8 each carry macOS, Linux and Windows
  deliverables. Their =:platform_status:= property records each platform
  separately (for example
  =macos=completed linux=planned windows=planned=), and the milestone =:status:= is
  =partially_completed= until all three are =completed=. A later milestone that
  needs only one platform's part names it in =:platform_prereqs:= (for example
  =GS5=macos=) and may start once those entries read =completed=, without
  waiting for the other platforms.

  *TCC.* Live macOS tests need Screen Recording / Accessibility grants for the
  signed GuiAssert helper bundle. When a grant is missing the implementing agent
  records =<milestone> BLOCKED: TCC <permission> for <binary>= in the
  milestone's Outstanding Tasks and continues with work that does not need it.

*** Deviations
    - =session-state= (spec §8.4) was not emitted as implemented: the spec
      did not say which id or =seq= it carries, since a session outlives the
      request that started it. Resolved in the review: §8.4 now makes it the
      one connection event (=id= null, a per-connection =seq=,
      =data.session=), sent when an owner session changes state on its own
      (checked every 250 ms by a prober thread running =session-info=) and
      when the daemon stops it at disconnect or shutdown; implemented and
      covered by =test_serve_session_state_events_for_owner_sessions=.
    - Byte parity of =session-start= masks =hostPid=, the pid of the newly
      started session host: two starts cannot have equal pids.
    - The vision verbs are implemented in GS2 over the pure core (their =data=
      is needed by =test_fixture_emits_every_documented_data_key=), except
      =vision-segment <video>=, which answers exit 4 (=not-implemented=;
      =not-compiled-in= in =guiassert-fixture=). GS4 implements video input
      and owns the vision tests.
    - =serve --listen unix:= is POSIX-only for now: Nim's standard library has
      no AF_UNIX on Windows, so there it answers exit 4 / =wrong-platform=;
      =--stdio= works everywhere. Follow-up with the Windows backends (GS11).
    - =--listen unix:= with an empty path means the default
      =<state-dir>/serve.sock= (the spec names the default, not its spelling).
      The state directory is made 0700 as every state directory is; a custom
      socket directory must already be 0700 and is refused otherwise rather
      than having its mode changed.
    - =ocr --image= reports the file as an =ImageRef= with =source.kind=
      ="file"=, its own size and SHA-256, =capturedAt= from its modification
      time, and =origin [0,0]= / =scale 1= (a file carries no desktop
      placement).
    - =wait= reports =elapsedMs= as the scheduled time of the matching attempt
      (=(attempt-1) * interval=), so the same wait yields the same envelope;
      the polls are paced by real time.
    - =session-stop= removes the record (a later =session-info= is exit 3);
      the returned =Session= says =stopped=.
    - In =guiassert-fixture= nothing is selected implicitly: with no selection
      the platform default applies and answers =not-compiled-in= (consumers
      set =GUIASSERT_BACKEND=fixture=).
    - =core/interfaces= gained what the verbs need: =BackendError.remedy=,
      =features= on every backend, =recordings= (capture), =focusWindow= /
      =setWindowBounds= (input), and =apps= / =launch= / =quit= /
      =permissions= (session). =core/desktop_types= gained =Permissions= and
      =Feature=.
    - =tests/tcore_purity.nim=: the per-module "the analysis saw import edges"
      sanity check exempts the modules named in =importFreeCoreModules=
      (=core/sha256=, which imports nothing). The review replaced a text
      probe for ="import "= (which a =from= import would have slipped past)
      with that explicit list, and the test now requires an exempt module to
      have zero edges and no import, from or include statement; every other
      core module must still show edges, and the allowlist check itself
      applies to all. The control on =image_math= still proves edge
      detection.
    - Review additions: every file GuiAssert reads on a caller's behalf is
      bounded (=state_store.readFileCapped=: records and scenarios 4 MiB,
      =type --text-file= 1 MiB, PNG files 256 MiB); an oversized file is
      =bad-args= / =invalid-value=. Scenario strictness (unknown keys at the
      top and nested) is now exercised by
      =test_unknown_verb_and_unknown_flag_are_bad_args=, with the oversized
      inputs.

*** Deviations
    - =vision-segment --frames --scale-width= reported the scaled size as
      =source.width= / =height=; the spec names the source, so it now reports
      the first frame's own size. A bug fix, not a contract change.
    - The defaults of =vision-segment= were not written in the spec. §7.5 now
      states them (threshold 0.35 on the most-changed cell of a 4x4 grid;
      frames at fps 1, unscaled; video at fps 2, scaled to 320 wide), together
      with what =source= and =params= report for a video and the video error
      mapping (no ffmpeg: exit 4 / =missing-tool=; not a video: exit 2 /
      =invalid-value=). These fill in what 1.0 left unstated; no shape or
      meaning of 1.0 changes, so the contract stays =guiassert-desktop/1.0=.
    - The video path decodes frames through ffmpeg's =gray= output rather
      than =video_analysis.segmentByChange= (which spawns ffmpeg per frame and
      imports =std/re=, whose PCRE library is loaded at program start).
      =segmentByChange= is unchanged; =segmentVideo= is the API the CLI
      equals.
    - =core/ssim.computeSsim= returned 1.0000000000000002 for identical
      images (its documentation promises exactly 1.0 and the range [-1, 1]);
      it now returns 1.0 for identical pixels and clamps to the range.
    - =tcontract_decisions= test_capabilities_vocabulary_and_details_feature:
      its =vision-segment <video>= exit-4 case now sets =FFMPEG_BIN= to a
      missing file, so the full binary answers exit 4 / =missing-tool= (it
      decodes video now) and the fixture binary =not-compiled-in=, both with
      feature =video-decode=.
    - The harness gained =siblingBin= and a =bin= argument to =runCli= /
      =cli= / =startServe= / =isMinimalBinary=, so a test can address one
      particular build.
    - Review fixes (2026-10-20): =segmentVideo= read ffmpeg's stderr only
      after stdout ended, so a video whose frames are damaged (ffmpeg logs
      every bad macroblock, ~130 KB for a 60 s clip) filled the stderr pipe
      and hung the verb forever; and =probeVideoSource= merged ffprobe's
      stderr into its JSON, so any warning turned a readable video into exit
      2. Both now drain stderr on a thread of their own, keeping the first
      4 KiB for the error message. The input is passed as
      =file:<absolute path>=, so a name starting with =-= or naming an
      ffmpeg protocol (=pipe:0=, =concat:=) is read as a file, and a path
      that is not a regular file (a FIFO) is refused (exit 2) instead of
      blocking ffprobe. An abandoned ffmpeg (cancel, deadline, decode error)
      is killed and reaped rather than sent SIGTERM with a 2 s grace.
    - =segmentVideo= and the legacy =video_analysis.segmentByChange= agree
      on segment boundaries (checked on four videos: two-state, three-state
      at an odd 334x210 size, a moving test pattern, a static one) but not
      on =changeScore= to the last digit (about 1%): the legacy path samples
      to RGB PNGs at =scale=W:-2= (even height) and converts to gray, the
      new one reads ffmpeg's gray plane at the rounded height. Not a defect;
      =segmentByChange= is unchanged and the CLI equals =segmentVideo=.
    - Follow-up hardening (2026-10-20, from origin/agents at 96710e5; the
      three items the GS4 review left open):
      1. Frame-size cap. One constant, =core/image.maxImagePixels= (2^28),
         now backs the PNG decoder (=maxPngPixels= is an alias) and caps the
         frame =segmentVideo= decodes (=FrameTooLargeError=, a =ValueError=,
         raised after ffprobe and before ffmpeg or any buffer), the scaled
         =--frames= frame and the legacy =decodeGray=. The CLI maps it to the
         existing exit 2 / =invalid-value=; no reason was added, and spec
         §7.5 states the cap as a clarification of 1.0. Before, a 16x2048
         video at =--scale-width 16384= asked for a 34 GB frame buffer and
         died with exit 1 / internal.
      2. Cancel granularity. =segmentVideo= now reads ffmpeg's stdout with
         =readOutput=, which waits in 50 ms slices (=poll= on POSIX;
         =PeekNamedPipe= and a 10 ms sleep on Windows, where an anonymous
         pipe cannot be polled) and runs the checkpoint between them, so a
         cancel or deadline is honoured within ~100 ms at any =--fps=. Spec
         §7.5 says so. The Windows branch compiles (=nim check --os:windows=)
         but has not run yet; it runs on the first Windows CI job.
      3. Safe input names. The =file:= helper moved to
         =media.ffmpegInputUrl= and every ffmpeg / ffprobe call in src/ that
         reads a caller's file uses it: =segmentVideo=, =probeVideoSource=,
         =probeImageSize=, =decodeGray=, the legacy =video_analysis= argv
         builders (=buildProbeArgv=, =buildSampleFramesArgv=,
         =buildExtractFrameArgv=, so =segmentByChange=, =probeVideo= and
         keyframe extraction), =vision_windows.buildCropArgv=, the two
         =media= composition argvs and the OCR preprocessing pass
         (=ocr.preprocessToPng=, added by the review). Not changed, by
         design: the editor backend (its =-i= inputs are TTS renders and
         segments in its own cache), =capture= (its
         =-i= values are device names such as =0:none= or =:0+100,50=, not
         files), the fixture capture backend and =contactSheet= (inputs are
         image2 patterns in GuiAssert's own temp directories). Output paths
         are not wrapped (see Outstanding Tasks). Deviation from the brief:
         the shared helper is =file:= & the path as given, not
         =file:<absolute path>=. ffmpeg strips one =file:= and opens the rest
         as a path, so a relative name is just as safe; making it absolute
         reads the current directory, which added =OSError= and effect tags to
         the legacy argv builders and broke their frozen API
         (tcore_shims, =raises: []= / =tags: []=).
      Found on the way: =probeImageSize= merged ffprobe's stderr into the
      text it parsed, so any ffprobe warning (here, ffmpeg's own "Picture size
      20000x20000 is invalid") made it fail to parse; and =decodeGray= never
      read ffmpeg's stderr, so a chatty decode could block on a full pipe.
      Both now run through =runCollecting= (stdout parsed alone, stderr
      drained on a thread, its first line kept for the error message), the
      helper =probeVideoSource= already used inline. The legacy API baseline
      (tcore_shims) still holds: no new raises or tags.

    - Linux (companion/linux, 2026-10-22). =focus= is not offered on GTK 4
      elements: GTK 4.20 answers Component.GrabFocus with NotSupported
      (measured), and the backend tells GTK 4 by its Application
      ToolkitName / Version. =scroll-to-visible= is offered by no Linux
      element: GTK 3 and GTK 4 refuse Component.ScrollTo (measured), and
      offering it would promise an action no measured toolkit performs.
    - Linux: =wait --element --pid N= (and =--app=) for an application not
      yet on the AT-SPI bus is exit 3 / =app= at once, as with the fixture
      backend, not a wait for it to register; a caller that waits for a
      starting application waits without a target, or polls =find --pid=.
    - Linux: Qt 6 Widgets labels implement no AT-SPI Text interface, so a
      Qt label's =text= is null (its words are its =name=); GTK labels have
      both. Qt registers on the AT-SPI bus only while
      =org.a11y.Status.IsEnabled= is true (the test session sets it, as an
      assistive technology does); a GuiAssert session backend that starts
      an AT-SPI bus for Qt clients sets it too (GS10).
    - Linux: =linux-host= is implemented ahead of GS10 for what GS7 needs of
      the caller's own session (see Deliverables); GS10 keeps its attach
      checks (=test_linux_host_attach_reports_existing_session=) and the
      private session backends.
    - Linux, request to the spec owner (=substrate/macos=), 2026-10-22: the
      §4.2 =tree= row of the Linux backend table could state how
      =linux-atspi= finds its bus and its geometry, which this share settled
      by measurement and which the contract leaves implicit: the bus is the
      one the invocation's environment names (=AT_SPI_BUS_ADDRESS=, else the
      session bus's =org.a11y.Bus=, asked without starting it), none being
      exit 6 / =atspi-disabled=; extents are read in window coordinates and
      placed through the window the session's capture backend reports (GTK 4,
      and GTK 3 on Wayland, give no screen coordinates), else =bounds: null=.
      Both follow from §5 and §7.3 as written, so no contract change is
      needed. (The implementing agent first wrote this into the spec; review
      reverted it, since the spec belongs to =substrate/macos=.)
    - Linux, review 2026-10-22: =dbus_wire= treats every message as hostile
      (any application on the bus can address this client): strings are
      checked for UTF-8 and NUL, object paths and signatures validated,
      header fields type-checked, fd passing refused, one message bounded to
      2^20 decoded values, and a message that is not the answer to a call in
      flight dropped from its header undecoded; a malformed one closes the
      connection. Pipelined reads are sent 64 objects at a time. An answer of
      an unexpected type is =tree-failed=, never an internal error.

*** Deviations
    - Linux (companion/linux, 2026-10-22). Scroll sign: the spec does not
      state it; the Linux backends scroll DOWN for =--dy= > 0 and RIGHT for
      =--dx= > 0 (wl_pointer's and libinput's convention; X buttons 5 / 7),
      =--unit line= as wheel notches, =--unit pixel= as smooth logical
      pixels. Request to the spec owner (=substrate/macos=): state the sign
      in §7.5 so macOS and Windows agree.
    - Linux: =linux-mutter= types only what the session's keyboard layout
      has (Mutter's RemoteDesktop picks a key for a keysym in the current
      layout and silently drops one it lacks); a key outside it is exit 4 /
      =unsupported-option= naming its position, never the character. A
      stock GNOME =us= layout maps the F13–F24 keys to XF86 launchers, so
      =key F13= there is exit 4 too; the private GNOME test session sets
      =org.gnome.desktop.input-sources xkb-options ['fkeys:basic_13-24']=,
      and switches off =org.gnome.mutter overlay-key= and Super+A, which
      otherwise open the overview on =key cmd+…=. Request to the spec owner:
      §7.5 could say that a backend refuses a key the session cannot produce
      with exit 4 / =unsupported-option= (which is what reject-don't-drop
      already implies).
    - Linux: =linux-mutter= needs PipeWire in the session for pointer
      motion (absolute motion is defined only against a screen-cast stream;
      every GNOME session runs PipeWire). Without its socket the pointer
      verbs are exit 4 / =missing-tool= before Mutter is asked: with the
      daemon gone Mutter's Start never answered and the shell stopped
      answering Eval (measured, GNOME Shell 49). Keys need no stream.
    - Linux: =linux-xtest= refuses =scroll --unit pixel= (exit 4 /
      =unsupported-option=): the X core protocol scrolls in notches only.
      =linux-uinput= reports =window-management= unavailable
      (=unsupported-option=), types with US-layout key codes, and refuses a
      character the US layout lacks; its positive path is untested here
      (BLOCKED, see Verification).
    - Linux: =linux-wlr-virtual= creates its devices per verb. A seat that
      gains the keyboard (or pointer) capability with the helper's device is
      given 400 ms before the first event, because clients bind their
      =wl_keyboard= only after the capability appears and keys sent before
      that are lost; a seat that already had the capability pays nothing.
      The helper first waits for what it can observe (a roundtrip, then its
      own connection seeing the capability); no protocol reports that
      ANOTHER client has bound its keyboard, so the rest is a bounded wait
      (review, 2026-10-23: with the wait removed, about one key verb in five
      on a headless sway lost its key and the key-table and typing tests
      went red; with it, none in every run). =click --modifiers= waits 30 ms
      between the modifiers and the pointer on =linux-mutter= only (Mutter
      applies a virtual keyboard's modifiers to pointer events a moment
      late and offers nothing to wait on; review: with no wait the first
      press of a modified double click lacked its modifiers in one of three
      runs) and on =linux-uinput= (two evdev devices, read with no order
      between them); =linux-wlr-virtual= and =linux-xtest= need none (one
      connection's requests are handled in order; review: 20 modified clicks
      with no wait on sway and Xvfb all carried their modifiers), so they
      no longer wait (as first implemented, every backend waited).
    - Linux: window management, which spec §7.5 puts in the input module, is
      sway's IPC on =linux-wlr-virtual= (sway only), core X requests on
      =linux-xtest=, and GNOME Shell's Eval on =linux-mutter= (unsafe mode
      only, like =linux-gnome='s window list).
    - Linux: =backends/tree/dbus_wire.nim= gained =ddictEntry= / =dvardict=
      constructors (Mutter's option dictionaries); =linux_gnome.eval= is
      exported for =linux-mutter='s window management. The tree fixture
      =tests/live/fixtures/atspi_form.c= gained =--input-log= (the input
      lab: a slider, a sketch pad and a key log that log the events they
      receive), off by default, so GS7's golden trees are unchanged.

*** Implementation Details
    - The session host is =guiassert __linux-session-host --state-dir <dir>
      <id>= (internal, like the fixture's =__session-host=), started with
      =linux_common.spawnDetached= (double fork, =setsid=, standard streams
      on =<state-dir>/sessions/<id>.log=, umask 077). It reads the record the
      starter wrote (state =starting=, =private.spec=), starts the server,
      then the AT-SPI bus, then writes =<id>.ready= (environment, runtime
      directory, VNC endpoint) or =<id>.failed= (its error). The starter waits
      for either, for the host's death, or for the readiness bound; on
      ready it reads the session's displays through the session's own
      capture backend (so the display server answers from the caller's side
      too), writes the record =running= and removes =<id>.ready=, which is
      the host's signal that the session was taken over. The host then
      supervises every 100 ms (its record still names it; the display
      server, its VNC server and the AT-SPI launcher still run) and tears the
      session down on SIGTERM, on a vanished record, on a dead server (after
      writing state =error= with =compositor-exited=, =window-manager-exited=
      or =vnc-exited=), or when no starter took the session over within 15 s.
    - Every process of a session carries =GUIASSERT_LINUX_SESSION_TAG=<128
      random bits>=, recorded in =private.tag=. Teardown (by the host, by
      =session-stop= of a session whose host died, by a failed start) ends
      exactly the processes carrying it (SIGTERM, SIGKILL after 2 s; SIGKILL
      at once for a start being undone, so the failure is reported within
      the 250 ms readiness margin), each signalled only while its pid still
      has the start time it was found with, and removes the runtime
      directories those processes named (=XDG_RUNTIME_DIR=), never the
      caller's, and only a =/tmp/guienv-*= or =/tmp/gaxv-*= directory of
      this user. Scanning /proc is done with raw reads of this user's own
      processes only (measured: 241 ms per scan reading every /proc/*/environ
      with exceptions on a 1225-process host, a few ms this way).
      Review, 2026-10-23: on this host at a load average of 60 one such walk
      still took 70-200 ms (~420 processes of this user, development-shell
      environments of tens of kilobytes), and a cut start made two, so its
      exit 5 came after the deadline; every session process is the host or
      a descendant of it, so the walks now skip, by their start time
      (field 22 of /proc/<pid>/stat), every process older than the host
      without reading its environment (=scanTagged=), and one walk gives
      both the processes and the directories they name.
    - Runtime directory (review, 2026-10-23): the host makes it before
      anything else, with mkdir(2) mode 0700 (failing when the name
      exists), at =/tmp/<prefix><the tag's first 64 bits>= (=guienv-= for
      linux-sway and linux-gnome, =gaxv-= for linux-xvfb;
      =sessionRuntimeDir=), and the server runs in it (=HostSpec.runtimeDir=;
      =desktop_env/sway= and =gnome= take a =runtimeDir=). The record's
      holder therefore finds it by the tag alone: a starter undoing a start
      whose host it killed before the host reported it, and session-stop
      after the host died, remove it even when no live process names it
      (Xvfb's environment never did). Removal goes through
      =desktop_env/runtime_dir.removeRuntimeTree=: the mounts below it are
      detached, an entry that cannot be removed does not stop the others,
      and it is retried for up to 2 s (100 ms on the start-undo path).
      The desktop-environment targets used directly (the GS5-GS8 live
      suites) also end, at =stop=, every process of this user that still
      names their runtime directory (=endClients=, default on): GNOME
      Shell's =ibus-daemon= rewrote =config/ibus/bus= after the directory
      was removed, and a busy document-portal mount made =removeDir= give up
      on the whole tree; the session servers pass =endClients = false=,
      their host's tag sweep being the rule there.
    - The session bus of a private session would activate at-spi2-core's own
      =org.a11y.Bus= launcher when a client asks for it first (the GTK
      portal backend does, while the sway target starts), and that launcher
      runs the host system's dbus-daemon path (see =atspiLauncherFor=). The
      host puts a data directory of its own first in =XDG_DATA_DIRS=, with
      an =org.a11y.Bus.service= naming the pinned launcher (D-Bus
      specification, "Message Bus Starting Services"), so activation and
      the host's own start run the same launcher. The sway target's
      plumbing (portal backend, bar) starts with =NO_AT_BRIDGE=1= (never in
      =Session.env=), so =apps= of a fresh sway session lists none of it.
    - Readiness timings measured here (load average 20-80): sway 0.4-0.5 s,
      Xvfb 0.15-0.4 s, GNOME Shell 1.3-2.7 s, all within the 10 s bound.
